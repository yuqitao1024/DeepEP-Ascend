1. 先建立通信心智模型

MoE 的 router 只决定 token 应该去哪个 expert。expert 分散在不同 rank 上时，DeepEP 还要把 token 发过去，再把 expert 输出送回原 rank。前一程是 dispatch，后一程是 combine。这两程都不是规则的矩阵 collective：每个 rank 发给谁、发多少，由这轮 top-k 路由结果决定。

Collective

所有参与者调用同一个集体操作。库通常知道完整参与集合和数据形状，例如 all-to-all。控制简单，但不一定适合细粒度、稀疏且动态的 token 流量。

One-sided

发送端直接描述“把本地这段数据写到 peer 的某个 offset”。接收端不必同时调用匹配的 recv，但双方必须先约定窗口布局、完成通知和内存序。

1.1 七个最常见的名词

名词在本仓里的含义容易混淆的点
communicatorPyTorch ProcessGroupHCCL 已建立的通信上下文，带 rank、world size 和 bootstrap 资源。DeepEP 借用 handle，不拥有 ProcessGroup 的生命周期。
team一组 rank 和 rank 映射。语义上可分 world、scale-up、scale-out。team 内 peer 编号不一定等于 world rank，必须翻译。
window各 rank 按相同逻辑布局注册的一段 device buffer。“对称”指布局和 offset 可复用，不要求虚拟地址数值相同。
channelHCOMM 为 AIV/UBC_CTP 建立的通信执行资源，内部关联 SQ/CQ、doorbell 和远端信息。channel 不是 stream；当前生产配置固定为 1 个。
request一批异步通信的完成句柄。DeviceRequest 已定义，但当前 staged 路径还没有真实状态机。
signal接收端可轮询的控制值，用 generation 表示本轮 payload 可见。signal 本身不能替代 payload 完成和 release/acquire。
flush / barrierflush 完成某个通信作用域内的已提交操作；barrier 让 team 成员在同一代际会合。flush 是操作完成边界，barrier 是参与者会合边界，不能互换。

1.2 为什么要用 symmetric window

假设每个 rank 都把接收区按 [source_rank][token_slot][hidden] 排列。发送端拿到本地窗口基址 B_local 和目标字段地址 P_local 后，先算偏移：

offset = P_local - B_local
remote_address(peer) = peer_window_base(peer) + offset

operator 只需要保存一个 offset，不必把每个 peer 的完整指针塞进路由元数据。窗口布局一旦变化，所有 rank 必须一起变化；这也是注册窗口和 topology epoch 要受生命周期约束的原因。

2. HCOMM host 资源和接口

Host 端先从 ProcessGroupHCCL 取 communicator，再用它创建 HCOMM 资源。入口在 deep_ep/utils/hccl.py：代码依次尝试 group 本身和 NPU backend 的 get_hccl_comm(local_rank)，只接受一个非零 communicator。这样可以复用框架已经完成的 rank bootstrap。

cann_compat.hpp 不是另一套业务抽象，而是 device service 读取 HCOMM 结构时使用的 ABI 镜像。所有结构都有 static_assert(sizeof(...))。升级 CANN 后，如果字段布局或结构大小变化，必须先重新验证兼容性，不能只改版本常量。

4.1 facade 的典型调用方式

DeviceTransportFacade transport(context, 0);  // 当前固定 channel 0
TeamPeer route = ...;                         // team + team-local peer

transport.system_fence();
transport.put(
    route.team, route.peer, remote_destination, local_source, bytes,
    CooperationScope::kParticipant, MemorySegment::kDevice,
    kDefaultOptions, RemoteAction::none());
transport.flush(CooperationScope::kDevice);
transport.put_value(
    route.team, route.peer, remote_count_address, count,
    sizeof(std::uint64_t), kDefaultOptions);
transport.signal(
    route.team, route.peer,
    RemoteAction::signal_set(release_signal_index, generation));

transport.wait_signal(
    source_route.team, source_route.peer, release_signal_index,
    generation, timeout_cycles);
auto ready_generation = transport.load_acquire(local_generation_address);

示例省略了地址边界、错误和零字节处理，但 facade 的参数顺序与源码一致。真实 kernel 还要为 world rank 选择 team、校验 offset、处理每个 peer 的 count，并让确定的 SIMT thread 负责 command publication。

5. staged transport 怎么执行

为什么多一层 staged service？CANN 9.2.0 的 AIN device 方法和 URMA doorbell 操作属于 AICore 执行环境；当前 DeepEP producer 是 SIMT VF，不能安全地直接调用 st_dev/ld_dev 敲 doorbell。因此 SIMT 只录制固定 ABI 的命令，AICore service 再翻译和执行。

5.1 staged transport 自己的 POD

结构体大小关键字段与作用
TransportCommand128 Bopcode/team/scope/segment/action，peer/world peer/channel，source/destination/bytes/value，signal index、offset、timeout。
TransportCommandQueue64 BABI、capacity、count、generation，以及 commands/service/diagnostic 的 device 地址。
TransportServiceState64 Bconsumed count、active、consumed generation、barrier generation 和 retry limit。
DeviceTransportDiagnostic64 B只记录首个错误：command、opcode、peer、channel、SQ/CQ head、backend status 和 generation。
StagedTransportContext64 BCANN compatibility、command queue、team、window 和 fetch result 地址。
DeviceRequest32 B四个 64 位 word 的预留状态。目前没有 pending/completed/error 生命周期。

5.2 AICore service 的工作顺序

  1. 校验 staged context、queue、service 和 diagnostic 的 ABI/version/size。
  2. 读取本轮 generation 和 command count，拒绝 overflow 或重复执行。
  3. 把 team-local peer 翻译为 world peer，检查 channel、window 和 remote buffer。
  4. 把 put/value/atomic/signal 转为 URMA SQE/SGE，写入 SQ 并敲 doorbell。
  5. 在 flush/barrier 边界 drain completion，轮询 CQ；超时或失败时只发布首个结构化错误。
  6. 全部命令消费完后更新 consumed_count 和 consumed_generation。

6. payload、control 与内存序

one-sided 通信最危险的 bug 不是“没发出去”，而是接收端先看到了 ready 标记，随后读到上一轮或未写完的 payload。DeepEP 用 generation 隔离轮次，并明确规定 payload 必须先于 count/generation/signal 对远端可见。

6.1 generation 为什么不能省

设 rank A 连续执行两轮，第 g 轮 signal 的值是 g。如果只有一个布尔 ready，第二轮可能读到第一轮遗留的 true。使用单调 generation 后，接收条件变成：

consume(g) only if acquire(signal) >= g
and acquire(remote_generation) == g

即使各 rank 到达时间不同，上一轮的通知也不会满足下一轮的条件。generation 还会进入 diagnostic，超时报告才能指出卡在哪一轮。

6.2 当前同步槽布局

逻辑对象索引使用位置

combine release signal1combine contribution 发布完毕。
保留 signal2, 3后续协议扩展，不能与 barrier 索引重叠。
scale-out barrier0跨节点逻辑 team 会合。
scale-up barrier1节点内 team 会合。

7. dispatch/combine 中的实际用法

7.1 Dispatch：把 router 输出变成 expert 输入

  1. 根据 top-k 和 rank/expert layout 算每个 token 的目标 peer、目标 expert 和 slot。
  2. producer 把 hidden、FP8 scale、top-k metadata 等写入对应 peer 的 dispatch inbox。
  3. 对 payload 做 flush，再发布 count/generation/signal。
  4. 接收端等所有所需 source 的 signal，consumer 校验 record 并排成 local expert 输入。
  5. epilogue 生成 tensor 和 handle；上层 grouped GEMM 使用这个布局做 expert 计算。

7.2 Combine：把 expert 输出送回原 token

  1. expert GEMM 完成后，handle 提供 origin rank、origin token 和 contributor 位置。
  2. producer 把 BF16 expert output 写回 origin rank 的 combine inbox。
  3. payload flush 后发布 contributor count/generation/signal。
  4. origin rank 等待所需 contributor，按 token 和 top-k 权重做 reduction，必要时加 bias。
  5. 输出恢复为进入 MoE 层前的 token 顺序，交给后续网络层。
为什么 combine 更难藏：combine 除了通信，还要等待 expert GEMM 的真实依赖，并执行回写后的多 contributor reduction。当前代表 case 的 combine 为 141.718 ms、reduced combine 为 169.704 ms，明显长于 dispatch 的 36.259 ms。只让网络异步，并不会自动消掉接收端归约和 epilogue。

8. 通信与计算怎么配合

“overlap”至少有三层，讨论时必须说清楚是哪一层。

层次做法本仓状态
同步执行compute stream 等整个 dispatch/combine 返回后再启动下一段计算。功能基线，也是当前代表性能 case 的口径。
算子级 stream overlapEP kernel 在 communication stream，上层独立计算在 compute stream；event 表达输入依赖和完成。已实现并完成双 rank 实机验收。
算子内部流水把 payload 切成 chunk，chunk 0 通信时生产 chunk 1；用 request/channel/CQ 独立推进。尚未实现。当前 staged service 仍按一个命令批次串行执行。

8.1 已经交付的算子级异步

Ascend ElasticBuffer 支持 previous_event、async_with_compute_stream 和 allocate_on_comm_stream。EP 工作进入独立 communication stream，返回的 event 持有 tensor、generation、diagnostic 和完成状态。上层可以在默认 compute stream 上安排不依赖 EP 输出的工作，再通过 event 建立消费边界。

previous = record_event(compute_stream)
outputs, event = buffer.dispatch(
    ...,
    previous_event=previous,
    async_with_compute_stream=True,
    allocate_on_comm_stream=True,
)

# compute stream 上运行与 dispatch 输出无关的计算
run_shared_expert_or_independent_compute()
event.current_stream_wait()  # 真正消费 outputs 前建立依赖

Phase 3E 最终任务 task_20260820_115539_278562813437 在两张卡上通过 21/21 用例。三次 warmup、七次测量的 median wall-time 收益分别为 8.6122% 和 8.1679%；profiler 看到不同物理 stream 上的 Conv3D 与 dispatch kernel 存在正重叠区间。这里证明的是“两个 stream 确实同时执行”，不是传输内部已有多 flight。

8.2 事件解决的是依赖，不是传输吞吐

event 能避免 host 同步，也能让不相关计算与 EP 同时在设备上运行。但当前一个 buffer 同时只允许一个 active operation；同一操作内部仍是 reset → producer → execute → consumer。因此“async API 返回得快”和“网络与本算子的 producer/consumer 已流水化”是两件事。

9. 当前能力边界

边界源码事实工程影响
异步 requestflush_async()、wait() 是空实现，kAsyncCompletion 未启用。不能在 operator 内提交多个独立 flight 后择机等待。
远端 getstaged get() 是空实现。当前生产协议应坚持 push，不得静默调用 get。
channel 数requested_channels == 1，facade 使用 channel 0。多个 chunk 无法自然映射到独立队列。
批次复用command queue 依赖单 generation 和 consumed_generation。下一轮覆盖前必须等本轮 service 消费，无法形成 ring。
buffer 并发一个 buffer 只允许一个 active operation。same-buffer multiflight 尚不支持。
epilogue 前依赖previous_event_before_epilogue 在 Ascend 路径被拒绝。不能在 producer/service 和 epilogue 之间插入外部 event。
多机物理路径有 2D topology 和 staged 协议，但 physical scale-out capability 未作为生产能力开放。单机逻辑模拟不能替代 RoCE/NIC/故障/teardown 验收。

9.1 当前性能数据回答不了 overlap 收益

现有 EP8 代表 case 是 ep-fp8-align128-bias0-hcopy1-prev0-async0-alloc0。名字里的 async0-alloc0 表示它走同步口径，因此下表可用于判断五个操作的相对瓶颈，不能拿来宣称 stream overlap 的收益。

expanded_dispatch38.641 ms239.422 GB/s确认 padding/copy 与 network 的资源关系。

10. 下一批高优先级任务

结论：下一阶段确实应该转向通信与计算 overlap，但不是直接“多开 channel”。算子级 overlap 已有；现在要从 P3.0 的阶段测量开始，再补 request 生命周期，最后做 chunk pipeline。combine 是首要观测对象，因为它在当前代表 case 中耗时最高。

P3.0阶段 profiler 与 overlap accounting

目标

具体操作
在不改变默认热路径的前提下，为 dispatch/combine 添加 generation-qualified device timing；记录 command count/bytes、SQ/CQ 深度、高水位、wait cycles 和 AIV/AIC 资源占用。报告同时给串行总和、实际 wall time和可重叠上界。

不承诺直接提速。它决定 P3.1/P3.2 是否值得做，以及 combine 应先优化通信还是 reduction。

P3.1真实 DeviceRequest、flush_async 和 wait

目标
让一个通信批次能处于 pending/completed/error 状态，而不是每次 flush 都同步 drain。
具体操作
定义 request ABI：slot、generation、提交 command 范围、目标 CQ tail、状态和错误；flush_async 发布批次并返回 request，wait 只等待该 request。补 stale/double-wait/reuse/timeout 规则，并启用 kAsyncCompletion。
交付边界
先支持单 channel、最多一个 pending request，把状态机做对；不要同时引入多 channel。
验收
host probe、device probe、错误注入和 production lifecycle 全通过；request 未完成时不能覆盖 command；错误稳定归因到 request generation。
预期收益
单独可能没有收益，甚至有少量管理开销。它是 P3.2 的必要依赖。

P3.2chunked / double-buffer 算子内部流水

目标
让 chunk i+1 的 producer、chunk i 的网络传输和 chunk i-1 的 consumer 同时推进。
具体操作
按 bytes 或 token slot 切 chunk；建立两个 command slot、两个 workspace/inbox staging slot 和独立 chunk generation；先在 dispatch 做双缓冲，再移植到 combine。尾 chunk 和零 token peer 要走同一状态机。
交付边界
第一版保持一个 operator active、一个 channel；通过 request 轮换 slot。不要提前开放 same-buffer multiflight。
验收
profiler 必须显示不同 chunk 的 producer/network/consumer 正重叠；所有 shape 与同步基线逐元素一致；收益按 144 cases 分布报告，不能只报最佳 case。
预期收益
取决于 P3.0 测得的可重叠比例。理论上限由 Tserial = Tp + Tn + Tc 与稳态 Tpipe ≈ max(Tp,Tn,Tc) 的差决定，还要扣除填充、排空和争用。

P3.3多 channel command/service 执行

目标
当单 channel 的 SQ/CQ 或 service drain 已被 P3.0 证明为瓶颈时，允许 peer/chunk 分散到多 channel。
具体操作
放开 requested_channels 校验；host 创建并发布 channel table；制定稳定映射，例如 channel = hash(peer, chunk) % C；每个 channel 维护独立 queue head、CQ target、diagnostic 和 backpressure。
交付边界
先做 1/2/4 channel sweep。不要把 channel 数与 AIV block 数绑定，也不要默认越多越快。
验收
channel 间无乱序破坏 release protocol；队列满时 fail closed 或 backpressure；同一 workload 下给出吞吐、尾延迟、SQ/CQ 高水位和资源占用。
预期收益
只有单 channel 饱和时才有直接收益。若瓶颈在 combine reduction，多 channel 可能无收益。

P3.4资源分区与端到端 expert compute overlap

目标
让 EP 的 AIV/service 资源与 expert GEMM、shared expert 或其他 AIC 计算互不挤占关键资源。
具体操作
分别 sweep EP blocks、service blocks、channel 数和 chunk 大小；记录 AIV/AIC、HBM、NoC、URMA 利用率。针对 dispatch→expert GEMM→combine 做端到端 timeline，不只测单个 operator。
交付边界
先固定可复现的 expert workload，再调资源；不要用纯 Conv3D capability case 替代真实 MoE 结论。
验收
端到端 MoE layer wall time 下降，p95 不回退；profiler 证明重叠，且 EP/compute 各自单独耗时的拉长在可解释范围内。
预期收益
现有双 stream 验收中位数约 8%，但真实 expert workload 的收益必须重新测，不能直接套用该数字。

P3.5same-buffer multiflight 与 epilogue 前依赖

目标
允许多 operation generation 同时在飞，并支持 previous_event_before_epilogue 这类更细依赖。
具体操作
为 queue、workspace、inbox control、diagnostic 和 retained tensor 建立 ring slot ownership；event 绑定 slot + generation；销毁时逐 slot 有界等待。
交付边界
必须在 P3.1/P3.2 的 request 和双 slot 已稳定后开始。
验收
覆盖乱序完成、异常、超时、destroy-pending、generation wrap 防护和 graph capture fail-closed；任何 slot 都不能被未完成 generation 覆盖。
预期收益
主要改善调度自由度和连续层吞吐，单次 operator latency 未必下降。

11.2 每个优化任务都要留下什么证据

  • 同一 commit、同一 extension hash、同一 workload fingerprint、同一设备拓扑。
  • 功能结果：输出一致性、边界 shape、零 token peer、timeout/error/teardown。
  • 性能结果：device mean/p50/p95、wall time、logical bytes、stage timing 和 profiler timeline。
  • 资源结果：block 数、channel 数、command count、SQ/CQ 高水位、AIV/AIC 与 HBM/NoC 指标。
  • 先报告一组五操作代表 case，再跑 144 cases。代表 case 用来快速定位，不替代完整验收。

11.3 如何判断“真的 overlap 了”

至少同时满足三条：profiler 的两段工作在物理时间轴上有正交集；overlapped wall time 小于同轮 serialized wall time；结果和同步基线一致。只看到两个 stream id、API 提前返回或单项 kernel 变短，都不够。

overlap_interval = max(0,
    min(comm_end, compute_end) - max(comm_start, compute_start))

wall_gain = (T_serialized - T_overlapped) / T_serialized

资源争用会让并行后的单项耗时变长，因此还要记录：

T_overlapped can be greater than max(T_comm_only, T_compute_only)
yet still be less than T_serialized.

为什么 SIMT producer 不直接操作 URMA SQ doorbell？

CANN 9.2.0 中相关 AIN/doorbell 能力属于 AICore 执行环境。当前 producer 是 __simt_vf__，所以先录 GM command，再由 AICore service 用支持的 builtin 提交。

为什么 signal(generation) 前必须先 flush payload？

否则接收端可能先观察到当前 generation，再读到未完成或上一轮的 payload。flush 和 release/acquire 共同建立 payload-before-control。

仓库是不是还没有通信计算 overlap？

不是。双 stream + event 的算子级 overlap 已实现并通过双 rank 实机验收。缺少的是 request 驱动的算子内部 chunk pipeline，以及多 channel/multiflight 等更细能力。

为什么 P3.0 排在多 channel 前面？

当前 combine 还包含 reduction 和 epilogue。没有 stage timing 就不知道瓶颈在 SQ/CQ、网络等待还是数据归约；盲目增加 channel 可能只会放大资源争用。

为什么 P3.1 单独完成时可能没有性能收益？

request 是表达 pending/completed/error 的控制能力。只有 P3.2 真正把相邻 chunk 的 producer、network 和 consumer 排成流水后，它才有机会转化为 wall-time 收益。

本专题是 DeepEP v2：从 MoE 专家并行到 Ascend 950 性能优化 的通信补充材料。结论以仓库源码和已归档实机证据为准；CANN/HCOMM 升级后应重新检查 ABI、capability 和性能数据。
