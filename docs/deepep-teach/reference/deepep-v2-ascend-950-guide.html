1. 阅读索引：六个判断

EP 分摊专家权重

大量专家分布在多卡，每个 token 只计算 top-k 专家。模型容量可以增长，但每卡只保存部分专家。

EP 引入两次数据搬运

router 后需要 dispatch，专家计算后需要 combine。通信模式接近不规则 all-to-all，负载由 token 路由决定。

DeepEP 不是 MoE 计算库

它负责 token shuffle、元数据、归并、通信资源和 overlap。router 与专家 grouped GEMM 由上层框架负责。

EPv2 以 Gin 为通信底座

NCCL communicator、对称窗口、LSA 和 GPU 发起的 GIN 让 kernel 能按 peer 选择本地直访或 RDMA。

Ascend 不能逐行翻译 CUDA

CANN 9.2 的公开 AIN 是 AICore 接口，SIMT VF 不能直接敲 URMA doorbell。本仓采用 SIMT 录命令、AICore 执行的 staged transport。

片上并行度已经打开

直接路径已从单个 AI Vector block 扩到可配置的 1 至 72 blocks。下一步要看 subgroup grouping、DataCopy 和 HCOMM 各阶段的实测占比。

2. MoE 与 EP：为什么要做专家并行

2.1 从 Dense FFN 到稀疏 MoE

Dense Transformer 的每个 token 都经过同一组 FFN 参数。MoE 把 FFN 替换成多个 expert，router 为 token 选择 top-k 个 routed experts，并给出归并权重。DeepSeekMoE 还引入细粒度 routed experts 和始终参与的 shared experts，用更细的专家组合提升专门化，同时用 shared experts 承接共通知识。[S1][S2]

输入 X: [T, H]
router(X) -> topk_idx [T, K], topk_weights [T, K]
Y_t = shared_experts(X_t) + sum(weight[t,k] * expert[topk_idx[t,k]](X_t))

稀疏激活省的是每个 token 的 FLOPs，不是全部参数的存储。256 个 routed experts 即使每次只激活 8 个，所有专家权重仍要放在设备上。单卡无法容纳或无法高效服务时，就要把专家切到多卡。

SGLang 的实际抽象就是 TopK -> Dispatcher.dispatch -> MoeRunner -> Dispatcher.combine，vLLM 也把 DeepEP 作为 all-to-all backend。这个边界很重要：DeepEP 输出适合 expert GEMM 的布局和每 expert token 数，但不拥有 expert 权重，也不决定 router 算法。[S7][S8]

3.1 dispatch 做了什么

  1. 从 topk_idx 计算目标 rank、目标 expert 和每 rank/expert 的 token 数。
  2. 为每个去重后的目标 rank 分配槽位。top-k 中多个 expert 位于同一 rank 时，payload 通常只需发一份，metadata 保留多个 expert lane。
  3. 把 hidden、可选 FP8 scale factor、expert id、权重和 origin token 信息写入目标 inbox。
  4. 在 payload 可见后发布 control/release，接收方构造紧凑或按 expert 对齐的输出。
  5. 返回 handle。cached dispatch 和 combine 复用其中的 slot、prefix、来源与顺序信息。

3.2 combine 做了什么

  1. expert runner 把每个 expert 的输出交给 combine。
  2. combine 按 dispatch handle 把记录送回 origin rank。
  3. 接收方恢复 origin token 顺序，对 top-k 贡献做 BF16 归并，可应用路由权重和 bias。
  4. allow_multiple_reduction 决定同一 contributor rank 上的多个 lane 如何归约；expanded/reduced 路径处理展开布局。

4.3 direct 与 hybrid

Direct mode 把 EP domain 看成一个目标 rank 集合。节点内 peer 可走对称地址的直接 load/store，跨节点 peer 通过 GIN 完成 put、signal 和 completion。路径短，适合拓扑和网络允许 full connection 的场景。

Hybrid mode 把 rank 表示为 (scaleout_rank, scaleup_rank)。kernel 先按 scale-out 目标组织 token，再由节点内 forwarder 使用 NVLink 转发到本节点对应 expert。它减少每个 GPU 的跨节点连接压力，也适配 group/node-limited routing。代价是多一级 buffer、channel metadata 和转发同步。

4.4 handle、JIT 和 overlap

  • 首次 dispatch 生成 handle；cached dispatch 避免重复部分 layout 工作，combine 用它恢复来源和顺序。
  • kernel 由轻量 JIT 在运行时按 dtype、top-k、hidden、rank 数和模式实例化，安装阶段无需编译全部 CUDA 组合。
  • previous_event、async_finish 和 communication stream 让上层把共享专家或其他计算与通信重叠。
  • get_theoretical_num_sms 根据受限流量和目标带宽估算 SM；get_theoretical_num_qps 在 direct/hybrid 下选择不同 QP 数，减少盲目 auto-tune。

5. H800 场景如何优化

这里的 H800 指上游 Hopper/SM90 实现和 V1 明确标注的 H800 平台。EPv2 README 的新数据按架构写作 SM90/SM100，因此不能把每个 V2 数字都改写成 H800 实测。

5.1 单机多卡：让 NVLink 和 SM 同时吃满

对称内存与 LSA

各 rank 注册同布局 window。kernel 用 rank 和 offset 计算 peer 地址，节点内走直接 load/store，省去 host 发起 collective。

warp 分工

warp 分别承担 notify、payload、forward 和 reduce。一个 warp 可对应一个 channel，减少控制分支互相阻塞。

top-k 去重

CUDA 用 warp match/deduplicate 把相同目标 rank 的 lane 分组，一份 token payload 只发一次，lane metadata 仍完整。

TMA 与异步 copy

hidden 主体通过 TMA 在 global/shared memory 间搬运，FP8 scale factor 使用对齐 copy，标量只处理尾部。

布局贴合 GEMM

expanded output 可按 expert alignment 填充并清零 gap，直接供 grouped GEMM 消费，减少框架侧二次 permute。

资源可控

峰值性能可增加 SM，在线推理 overlap 则保留更少 SM 给计算。combine 复用 dispatch 的 SM 选择。

5.2 多机多卡：分开处理 scale-up 和 scale-out

  1. router 用 node-limited routing 控制每 token 触达节点数，先从模型层减少 RDMA 扇出。
  2. 同节点使用 NVLink/LSA，跨节点使用 NCCL Gin。window 隐藏地址注册差异，operator 保留 put、signal、flush 等明确语义。
  3. hybrid dispatch 让 scale-out warp 发送到目标节点，再由 forward warp 分发到目标 GPU；combine 反向执行。
  4. 每 channel/QP 并行推进 RDMA，payload 完成后通过 release signal 发布 tail，避免 control 先于数据可见。
  5. FP8 dispatch 降低正向通信字节，combine 保持 BF16 归并精度。事件和独立通信流把 all-to-all 藏在共享 expert 或其他计算后面。

5.3 Gin 的依赖与运行语义

Gin 是 NCCL Device API 的 GPU-Initiated Networking 层。DeepEP v2 要求 NCCL 2.30.4 及以上，并用已有 NCCL communicator 创建 device communicator、team 和 window。它不是普通 host collective 的别名，而是让 GPU kernel 发起远端内存操作。[S4][S6]

6. Ascend 950：如何实现类 Gin 路径

6.1 不能直接复刻 Gin 的原因

CANN 9.2.0 的 AIN 提供 window、team、Put、Get、PutValue、Signal、Flush、Wait 和 barrier 等语义，表面上接近 Gin。但其 device 方法带 __aicore__ 资格，DeepEP 当前 operator 的通信生产者是 __simt_vf__。更关键的是，URMA SQ/CQ doorbell 需要 st_dev/ld_dev，这些 builtin 不能从 SIMT VF 安全调用。用普通非缓存 global store 假装 doorbell 没有 CANN 参考实现支持，存在静默丢命令风险。[S10][S11]

6.4 单机多卡的实现状态与优化方向

  • Host 端创建 HCCL scale-up team、一个持久对称 window 和每 remote peer 的 AIV UBC_CTP channel。
  • window 按 control/generation、dispatch inbox、combine inbox 和扩展区划分。每个 destination 为每个 source 保留固定 shard，发送端无需远端分配。
  • 64 位 generation 隔离重复调用；payload 写完后才能发布 count/completion。timeout 返回 rank、peer、command、channel 和 generation。
  • BF16、FP8、expanded/cached dispatch、combine、多 reduction、previous event、async 和 comm stream 已纳入 144-case 基准交集。
  • 4/8 rank 的公开 smoke 已有历史记录，但完整不对称、近容量、失败和 teardown 矩阵仍是拓扑 qualification gap。
当前资源占用：direct dispatch/combine 仍固定启动 1 个 __vector__ block、512 个 SIMT threads，benchmark 传 num_sms=1。Ascend 950PR_9599 每设备有 72 个 AI Vector 资源，主数据路径只用了其中一个执行域。这是 8 个优化项的共同起点。

6.5 多机多卡的实现状态与优化方向

设计上，rank 用 row-major (scaleout_rank, scaleup_rank) 表示。scale-up team 处理本节点卡间路径，scale-out team 处理同 rail 的跨节点路径，hybrid 路由可覆盖 local、scale-up、scale-out rail 和 diagonal 四类 route。physical scale-out 还需要 RoCE NIC 选择、远端注册、链路错误、地址发布和 teardown。

NPU8P 只有一个物理主机。仓库做过 4 rank 的 logical-single-host 两节点模拟，能够证明拓扑翻译、command 和 operator 逻辑，却不能证明 RoCE 数据面、NIC 亲和性、跨机故障或性能。因此 physical multi-host capability 仍应保持 disabled。mapped CPU elastic buffer 也缺少公开、完整的 host map/unmap 与 CPU/NPU release-acquire cache visibility 契约。[S13]

8. 性能对比口径和证据边界

8.1 H800 x 8 与 Ascend x 8 的统一 workload

正式对标固定为 DeepEP v2 README 的每 rank 最大 8192 tokens、hidden 7168、top-k 8、256 routed experts、FP8 dispatch 和 BF16 combine。H800 与 Ascend 都使用 8 个本地 rank、30 次 warmup 和 30 次 measurement。先运行上游首个 FP8 case 的 representative profile，确认 5 个操作的 workload、logical bytes 和计时协议一致；这一步只是预检。正式性能结论来自 canonical 的全部 144 cases，共 720 条逐项对比的 operation records。[S15]

8.2 为什么必须重新运行 H800

DeepEP v2 公开表没有 H800/SM90 单机 EP8 数据；公开的 SM90 项是带 CX7 的 EP 8 x 2 和 EP 8 x 4，多机 RDMA 拓扑不能替代 H800 单机 8 卡 NVLink 实测。因此当前文档不预填 H800 或 Ascend 数字，也不从其他版本换算目标带宽。正式数据只接受当前自动化生成、workload fingerprint 相同的两份 benchmark.json。

正式对比顺序：H800 representative 先生成 workload manifest，Ascend representative 原样消费并完成 5 个操作的契约预检；预检不产生正式性能结论。随后两端用同一 workload 运行 144-case canonical，逐项比较全部 720 条记录。tests/benchmark/compare_ep.py 会校验 schema、fingerprint、case IDs、logical bytes、mean/p50/p95 和 aggregated logical GB/s。任何缺 case、超时或 fingerprint 不一致都拒绝比较。

9. 8 个白盒优化项与分工建议

优先级不是八个人同时改两个大 kernel。先补 stage profiler，再建立多 kernel 全局同步边界。P0.1 是其余数据并行工作的地基；P0.2 和 P0.3 决定最大重复计算与内存效率；metadata 和 HCOMM 优化随后按 profiler 结果推进。

P0.1 从 1 个 AI Vector 扩到多 block 数据流水

现状
dispatch/combine 只有 1 个 vector block、512 threads，72 个 AI Vector 只用 1 个。
方案
拆分 one-block control kernel 与 data-grid kernel。所有数据阶段使用 global thread/stride；同 stream 的 kernel 顺序作为全局阶段边界，禁止跨 block 自旋 barrier。

dispatch.asc、combine.asc、tiling.hpp、runtime.cpp、elastic_buffer.hpp
依赖
先增加逐 stage event 和 active block/AI Vector profiler；定义 control/data block ABI 与 workspace checked arithmetic。
验收
72-block 代表 case 正确；profiler 显示多个 AI Vector 活跃；重复测量覆盖目标 stage 和未修改的公共操作，不设置固定百分比门槛。
风险
重复发布 control、跨 block 未完成就进入 epilogue、占满 AI Vector 破坏计算通信 overlap。

P0.2 实现 match_any 等价的 top-k subgroup grouping

现状
相同目标或 contributor 通过 world_size/top-k 重复扫描。正式 workload 下，combine 最坏约执行 37.58 亿次 rank/lane check。
方案
封装 active lane 按 integer key 分组、确定 owner、broadcast slot、active/unique mask，并定义 -1 lane。优先用已验证原生 SIMT primitive，否则用 ballot+shuffle 构造。
文件
新建 backend-local subgroup helper，并替换 dispatch slot assignment 与 combine contributor scan。
依赖
P0.1 的 data grid；需独立 compile probe 覆盖 partial active mask、重复 key 和 invalid lane。
验收
每个 unique rank 只有一个 owner；multiple reduction 行为不变；combine 不再对每个 hidden element 扫描 world_size * topk。
风险
Ascend subgroup 宽度或 mask 语义与 CUDA warp 不同，容易产生静默 slot 冲突。

P0.3 把标量 payload copy 改为 vector/DataCopy

现状
一个 SIMT thread 在标量循环中复制 hidden bytes/BF16，global memory transaction 低效。
方案
对齐主体采用最大已验证 vector transaction 或 GM-UB DataCopy，必要时双缓冲；标量只处理尾部。FP8 scale factor 保留 token/pack 与列主序 stride。
依赖
P0.1 的 disjoint tile ownership；先证明 symmetric record alignment 和 canonical H7168 的整齐路径。
验收
canonical hidden 完全走向量路径；BF16、FP8 行/列 scale layout 全过；重复测量能分离 copy stage 收益和端到端变化。
风险
越界读取、UB 容量、FP8 scale factor stride 被错误合并、expanded padding 未清零。

P1.4 并行或批量化 HCOMM publication

现状
thread 0 串行遍历 peer，put payload、flush、发布 control、等待 release、执行 barrier。
方案
先将 command construction、AICore service、payload completion、remote release 和 barrier 分段计时。对独立 peer 批量建命令，最少 flush 后按确定 rank 顺序发布 control。
依赖
P0.1 阶段边界和 profiler。若 transport stage 占比不高，保留串行实现并记录证据。
验收
payload-before-control ordering 不变；独立 peer 有并发或 batch 证据；100 generations 无 stale state。
风险
为了并发破坏 release ordering、command buffer 溢出、不同 channel completion 被错误合并。

P1.5 重写 expert counting 和 expanded destination assignment

现状
32 个 expert owner 各自重扫所有 record 和 top-k lane，大部分线程空闲，record 被重复读取。
方案
按 record 分片做 histogram，确定性 prefix 计算 expert range，再 scatter 到 expanded destination。atomic 只用于中间 count，最终顺序由 prefix/scatter 决定。
依赖
P0.1 data grid；可复用 P0.2 grouping；workspace 要做 overflow 和 alignment 检查。
验收
每个 top-k entry 有界读取；expert count、prefix、padding 和 byte ordering 与现有输出一致。
风险
atomic 完成顺序渗入 public ordering，导致 cached handle 或 grouped GEMM layout 改变。

P1.6 并行 combine planning、validation 与 contributor list

现状
8 个 destination/contributor owner 扫描 rows/records，504/512 threads 在 metadata stage 空闲。
方案
row/record partition 覆盖全 data grid，构造每 token 的 compact contributor list。错误候选写私有槽，再按原 rank/record/lane 次序做确定性 first-error reduction。
依赖
P0.1；compact contributor 去重依赖 P0.2。
验收
reduction 只遍历 compact list；masked route、multiple reduction 0/1、bias 0/1/2 与错误优先级不变。
风险
并行 validation 改变首错诊断，或 contributor 去重漏掉同 rank 多 expert 的合法贡献。

P2.7 重写 dispatch route planning

现状
8 个 destination owner 各扫 8192 tokens x 8 lanes，按 rank 串行分配 slot。
方案
每个 token 的 top-k 读取一次，经 subgroup grouping 产生 unique destination；随后 count、deterministic prefix、scatter 分配 slot。
依赖
P0.1 和 P0.2。建议与 P1.5 共享 prefix/scatter primitives，不共享 public metadata 语义。
验收
destination slot、rank prefix、handle 和 cached dispatch byte-for-byte 兼容；重复测量能分离 route stage 收益和端到端变化。
风险
使用 atomic 返回值作为最终 slot 会让顺序不确定，破坏 cached combine。

P2.8 并行 dispatch receive validation

现状
8 个 source owner 各自串行验证整个 receive shard，shard 大时尾延迟明显。
方案
按 record 分配给全 data grid，分别验证 ABI、generation、origin、expert、slot 和边界；最后做确定性 first-error reduction。
依赖
P0.1；错误归约 helper 可与 P1.6 共用。
验收
正常、empty、asymmetric、near-capacity 与故障注入路径一致；错误仍报告原 source/record/lane。
风险
过度拆分产生 kernel launch overhead。性能成熟后只融合无全局依赖且 ownership 兼容的阶段。

串讲结束后的检查题

为什么先做 P0.1，而不是先给 HCOMM 多开几个 channel？

当前主数据路径只用 1/72 AI Vector，数据 copy、route 和 reduce 都被片上并行度限制。没有 stage profiler 前，无法证明 HCOMM submission 是主瓶颈。先建立多 kernel 全局边界和多 block 数据网格，后续优化才有正确的执行载体。

为什么 physical multi-host 能力仍不能打开？

单机上的 logical two-host 只能验证 rank translation 和算法控制流。它没有验证 RoCE 地址、NIC 选择、跨机注册、链路故障、cache visibility 或性能。

拿到 H800 benchmark.json 后，第一步比什么？

先比 schema、formula version、world size、workload fingerprint、case IDs、operation IDs 和 logical bytes。身份不一致时不看性能数字。

评审或排障时，请附章节号、commit、设备拓扑和相关日志。性能问题还应附上 manifest 与 stage trace，避免不同工作负载的结论混在一起。

本材料是代码导读和协作手册，不替代各 phase 的 acceptance 文档。能力状态以当前仓库、TaskQueue 证据和正式 benchmark artifact 为准。
