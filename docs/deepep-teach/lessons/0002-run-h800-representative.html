DeepEP 实机课 · H800 x 8

编译 CUDA 包，跑完一个 representative case

目标很具体：在一台八卡 H800 服务器上编译当前仓库的 CUDA extension，运行 ep-fp8-align128-bias0-hcopy1-prev0-async0-alloc0，拿到五个操作的耗时和逻辑带宽。

单机 8 卡 FP8 dispatch BF16 combine 30 warmups + 30 measurements

1. 这次到底测什么

项目固定值
设备单机 NVIDIA H800 x 8，rank 0 到 rank 7
Caseep-fp8-align128-bias0-hcopy1-prev0-async0-alloc0
Workload每 rank 最多 8192 tokens，hidden 7168，top-k 8，256 experts，seed 0
精度FP8 dispatch，BF16 combine
计时CUDA event；每个操作 30 次 warmup，30 次 measurement；跨 rank 取最大 latency
输出dispatch、expanded_dispatch、cached_dispatch、combine、reduced_combine
口径说明：这是 144 cases 中的一项，用来做跨平台 representative precheck。它可以与当前 Ascend 代表 case 逐项比较，但不能代替 144-case 正式验收。

2. 运行前提

下面的复制块从仓库根目录运行。服务器需要满足这些条件：

  • 八张 GPU 的设备名包含 H800，并且当前用户有权访问 GPU 0 到 GPU 7。
  • 系统有 CUDA toolkit，nvcc 版本不低于 12.3。
  • 当前 Python 环境已经安装 CUDA 版 PyTorch 2.10 或更高版本。PyTorch wheel 必须按服务器镜像和驱动安装，这一步不适合由通用脚本猜测。
  • NCCL 2.30.4 或更高版本必须在实际运行时提供 Gin。使用跨节点或网络 Gin 时，还需要可用的 RDMA 网卡、驱动和网络插件，并启用 GPUDirect RDMA；只安装 NCCL wheel 不能保证 Gin 可用。
  • 机器能访问 PyPI 和 GitHub；如果是离线环境，需要提前准备 NCCL、NVSHMEM wheel 和 third-party/fmt 子模块。
  • 至少有一个空闲 TCP 端口。教程固定使用 8361。

如果仓库还没传到 H800 机器，先 clone，并切到团队指定的 commit。不要在不同 commit 上比较 H800 和 Ascend。

git clone --recurse-submodules <DeepEP-Ascend 仓库地址>
cd DeepEP-Ascend
git rev-parse HEAD

4. 命令做了哪些事

4.1 根据 PyTorch CUDA 版本选择 wheel

torch.version.cuda 是 PyTorch wheel 的 CUDA family。复制块从中取 major，并安装同 family 的 NCCL 2.30.4 和 NVSHMEM 3.3.20。例如 PyTorch 报 CUDA 12.x 时，安装包名是 nvidia-nccl-cu12 和 nvidia-nvshmem-cu12。

当前 CUDA extension 即使只跑 EPv2，也会在构建阶段链接 legacy NVSHMEM 源码和静态 device library。因此不能因为 representative case 使用 NCCL Gin 就省掉 NVSHMEM 安装。

4.2 强制编译 SM90 CUDA extension

H800 是 Hopper 架构，编译目标是 TORCH_CUDA_ARCH_LIST=9.0。--inplace --force 会在当前源码树重新生成 deep_ep/_C*.so，避免误用之前留下的 Ascend extension。编译完成后的 import 必须打印：

DeepEP platform: cuda
Device 0: NVIDIA H800 ...

4.3 先用 2 rank 判断 Gin 能力

check_cuda_gin.py 使用小 shape 依次探测 direct Gin、hybrid Gin 和禁用 Gin 的基础路径。只有 direct Gin 成功时才返回 0 并继续正式测试；其他情况会停止，避免自动切换通信模式后仍把结果当作同一口径。

脚本结论含义和下一步
DIRECT_GIN_AVAILABLEdirect Gin 可用，可以继续当前 representative parity 测试。
HYBRID_GIN_ONLYdirect Gin 不可用而 hybrid Gin 可用，通常表示 multi-plane/multi-rail 网络与当前 direct parity 口径不匹配。检查网络配置，或者为 hybrid 测试建立单独口径。
GIN_UNAVAILABLE_BASE_RUNTIME_OKdirect 和 hybrid Gin 都不可用，但禁用 Gin 后基础路径成功。重点检查 NCCL network plugin、RDMA 和 GPUDirect RDMA。
PROBE_FAILED探针遇到的不是已知 Gin unavailable 错误，例如 OOM 或设备映射错误。直接查看对应日志，不要按网络问题处理。

探针日志保存在结果目录的 gin-preflight/direct.log、hybrid.log 和 fallback.log。脚本按需执行，已经得到结论后不会继续运行无关探针。

4.4 benchmark wrapper 固定测试合同

不要直接手写 8192、7168、top-k 8 等参数调用 tests/elastic/test_ep.py。统一入口 tests/benchmark/run_ep.py 会选择固定 case，生成 workload fingerprint，验证设备名包含 H800，并检查五条 operation record 都存在。

5. 成功后会得到什么

benchmark.md 的结果区应有五行：

Operation在 MoE 流程中的含义
dispatch普通 FP8 token dispatch。
expanded_dispatch带 expert alignment 展开布局的 dispatch。
cached_dispatch复用第一次 dispatch 生成的 handle。

6. 常见失败怎么处理

报错或现象原因处理
Cannot find package: ncclNCCL wheel 没装进当前 Python 环境，或 pip/python 不是同一个环境。始终用 python3 -m pip 安装，并检查 python3 -m pip show nvidia-nccl-cu12 或 cu13。
Cannot find package: nvshmemNVSHMEM wheel 缺失，或使用了另一个 Python。安装与 torch.version.cuda major 相同的 nvidia-nvshmem-cuXX==3.3.20。
Duplicate NCCL runtime / Invalid NCCL versionsPyTorch 加载的 NCCL 与 DeepEP 链接的 NCCL 不一致，常见于系统库、conda 库和 pip wheel 混用。清理 LD_LIBRARY_PATH 中多余 NCCL，使用同一 Python 环境重装 PyTorch/NCCL。不要关闭检查。
NCCL Gin is unavailable当前 NCCL communicator 没有提供可用的 Gin 类型。版本号满足要求也可能因 NVLink、RDMA、驱动、网络插件或多平面网络配置而不可用。查看 gin-preflight/ 中的自动判定和日志，再检查 nvidia-smi topo -m、RDMA 设备、GPUDirect RDMA 和 NCCL 实际选择的网络插件。脚本中的 EP_DISABLE_GIN=1 仅用于诊断基础路径，不会用于正式 representative case。
fmt/core.h: No such filethird-party/fmt 子模块未初始化。运行 git submodule update --init third-party/fmt。
cuda/std/... 或 CCCL header 缺失CUDA_HOME 指向 runtime-only 目录，或 toolkit 不完整。指向包含 bin/nvcc 和 include/cccl 的 CUDA toolkit。
初始化卡住或 Address already in useMASTER_PORT=8361 被其他任务占用。八个进程都结束后换一个空闲端口，例如 export MASTER_PORT=18361，再整体重跑。
设备名校验失败可见设备不是八张 H800，或 MIG/容器映射改变了设备名和数量。先修正容器 GPU 映射和 CUDA_VISIBLE_DEVICES。不要修改报告校验器伪装设备。
结果目录已存在 benchmark 文件wrapper 拒绝覆盖历史报告。使用新的时间戳目录。复制块默认已经这样处理。

7. 跑完后的自检

问题 1：为什么不直接运行 python tests/elastic/test_ep.py？
统一 wrapper 会固定 representative profile、生成 workload fingerprint、验证 H800 设备和报告 schema，并以原子方式发布最终 JSON/Markdown。直接调用底层脚本更容易漏参数。
问题 2：为什么单机 H800 测试仍要安装 NVSHMEM？
当前 CUDA extension 的构建仍包含 legacy NVSHMEM 源码和 device static library。代表 case 运行时走 NCCL Gin，不等于构建时可以缺少 NVSHMEM。
问题 3：哪份文件应传给 Ascend 侧锁定相同 workload？
workload.json。Ascend wrapper 使用 --workload-manifest 读取它，并验证内容与 representative profile 完全一致。
