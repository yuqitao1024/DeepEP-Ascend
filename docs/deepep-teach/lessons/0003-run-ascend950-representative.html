DeepEP 实机课 · Ascend 950 x 8

编译 Ascend 包，跑完同一个 representative case

这次在八张 Ascend 950 上运行与 H800 相同的 workload。命令加载 CANN 9.2.0 和固定 HCOMM，编译 Ascend extension，启动 8 个 HCCL rank，再输出五个操作的耗时和逻辑带宽。

单机 8 卡 72 AI Vector blocks FP8 dispatch BF16 combine

1. 对齐 H800 的测试合同

推荐做法：把 H800 结果目录中的 workload.json 传到 Ascend 机器，并在运行前设置 DEEPEP_H800_MANIFEST。wrapper 会逐字段验证它，不一致时直接退出。

2. 运行前提

  • 当前 shell 运行在有八张 Ascend 950 的机器上，NPU 0 到 NPU 7 都空闲且可访问。
  • 系统 CANN 路径是 /usr/local/Ascend/cann-9.2.0。
  • 验证过的 HCOMM 路径是 /home/pyptouser/yuqitao/Ascend/hcomm-deepep-current/cann。
  • Python 环境是 /home/pyptouser/yuqitao/venvs/deepep-ascend-py310，其中包含 PyTorch 2.10、Torch-NPU 2.10 和 pybind11。
  • 命令从 DeepEP-Ascend 仓库根目录执行。

如果你的机器使用不同的安装目录，只改复制块开头的 DEEPEP_CANN_ENV、HCOMM_ROOT、DEEPEP_CMAKE_ROOT 和 DEEPEP_PYTHON_ENV。不要只替换一半 HCOMM 路径。

2.1 可选：先放好 H800 manifest

H800 和 Ascend 不在同一台机器时，先传输文件：

scp /path/to/h800-result/workload.json \
  ascend-host:/path/to/ascend950-workload.json

进入 Ascend 机器后设置：

export DEEPEP_H800_MANIFEST=/path/to/ascend950-workload.json

如果不设置，下面的 wrapper 会生成 representative profile 的确定性 manifest。它的 workload 字段相同，但正式比较前仍应核对两边 fingerprint。

4. 为什么要把环境和运行放在同一个 shell

CANN 的 set_env.sh 先提供系统 runtime、compiler 和 HCCL。随后复制块把 hcomm-deepep-current 的 include、lib64 和 Python package 放到搜索路径前面。编译器看到的 HCOMM 结构体布局必须与运行时加载的 libhcomm.so 一致。

如果在一个 shell 编译，换到另一个没有 HCOMM export 的 shell 运行，程序可能加载系统中的另一份 shared library。最好的结果是 import 或 ABI 检查报错；更差的情况是通信阶段才超时。

5. wrapper 实际启动了什么

复制块调用的入口很短：

python tests/benchmark/run_ep.py \
  --backend ascend \
  --profile representative \
  --workload-manifest /path/to/h800/workload.json \
  --output-dir /path/to/new/result-dir

wrapper 会先检查 144 个 Ascend case 都是 supported，然后展开为：

python -m torch.distributed.run \
  --standalone \
  --nproc-per-node=8 \
  tests/ascend/benchmark/bench_ep.py \
  --num-sms 72 \
  --num-tokens 8192 \
  --hidden 7168 \
  --num-topk 8 \
  --num-experts 256 \
  --warmups 30 \
  --iterations 30 \
  --cases ep-fp8-align128-bias0-hcopy1-prev0-async0-alloc0 \
  ...

不要直接复制展开后的长命令作为日常入口。统一 wrapper 还负责 workload 校验、报告 schema、临时文件和失败日志。

6.1 生成 H800 与 Ascend 对比表

两边都成功后，在任一普通 Python 环境运行：

python3 tests/benchmark/compare_ep.py \
  --cuda /path/to/h800/benchmark.json \
  --ascend /path/to/ascend950/benchmark.json \
  --output /path/to/representative-comparison.md

比较器会检查 profile、world size、workload fingerprint、case ID、operation ID、logical bytes 和计时协议。任何一项不同都不会生成比值。

7. 常见失败

报错或现象原因处理
ASCEND_HOME_PATH 为空CANN 环境没有加载，或加载了错误的脚本。确认 DEEPEP_CANN_ENV 指向 CANN 9.2.0 的 set_env.sh。
import torch_npu 失败Python 环境未激活，或 PyTorch/Torch-NPU 版本不匹配。重新加载指定 venv，核对两个包都为团队验证版本。
只能看到部分 NPU当前 shell 的设备可见范围受限，或设备没有分配给当前进程。先恢复八张设备可见性。不要把 world size 改小后继续当作八卡结果。
extension 平台不是 ascend源码树里仍是 CUDA extension，或 build 没有强制执行。保留 DEEP_EP_PLATFORM=ascend 和 --force，检查编译日志的 Platform 行。
HCOMM ABI、symbol 或 protocol 错误HCOMM headers 和 shared library 来自不同目录。只保留一个 HCOMM_ROOT，确认所有 include/lib/Python 路径都由它派生。
HCCL 初始化超时某个 rank 没启动、设备绑定错误、旧进程仍占资源或通信环境异常。检查 run.log 中第一个失败 rank，确认没有遗留 8-rank 进程，再重跑新结果目录。
workload manifest does not match传入的文件不是当前 representative profile，或文件被改过。使用 H800 教程生成的原始 workload.json，不要手工编辑。

8. 跑完后的自检

问题 1：为什么优先复用 H800 的 workload.json？
它把 shape、seed 和路由 workload 固定为同一份输入合同。比较器还会检查 fingerprint，避免只看参数文字相同却实际输入不同。
问题 2：Ascend 的 num_qps=0 是否表示没有通信资源？
不是。QP 是 CUDA 侧调参字段。Ascend 侧由 HCOMM 管理 team、window、channel 和底层通信队列，报告中的 CUDA QP 字段固定为 0。
问题 3：为什么不能把两卡结果与八卡 H800 直接算比值？
world size 会改变每 rank 的目标集合、logical bytes 和通信拓扑。比较器要求 world size、fingerprint、case 和 operation 全部一致。
