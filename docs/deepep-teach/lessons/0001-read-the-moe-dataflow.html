DeepEP 导学 0001 · 约 15 分钟

读懂一条 MoE 数据流

读完后，你应该能在白板上画出 router、dispatch、专家计算和 combine，并准确指出 DeepEP 负责哪两段。

先看完整路径

1. Router为每个 token 选 top-k 专家，产生 expert id 和权重。
2. Dispatch按专家所在 rank 重排并发送 token。
3. Expert GEMM本 rank 的专家处理收到的 token。
4. Combine把结果送回 token 原 rank，按路由权重归并。
DeepEP 的边界：主要负责 dispatch 和 combine，以及两者依赖的 barrier、窗口、事件和通信流。router 与专家 GEMM 属于模型或推理框架。

为什么需要 EP

MoE 让模型拥有很多专家，但每个 token 只激活少量专家。稀疏激活降低了单 token 的计算量，却没有降低所有专家权重的总显存需求。把不同专家放到不同加速卡上，就是 Expert Parallelism。代价是：router 选中的专家经常不在 token 当前所在的卡上，所以每个 MoE 层都出现一次发散的 all-to-all 和一次反向归并。

一个最小例子

rank 0 持有 token A、B，专家 E0、E1
rank 1 持有 token C、D，专家 E2、E3

router(A) = {E0, E3}

dispatch: A 留一份给本地 E0，同时发一份到 rank 1 的 E3
expert:   E0(A) 与 E3(A) 分别计算
combine:  E3(A) 的结果返回 rank 0，与 E0(A) 按权重相加

top-k 大于 1 时，一个 token 会复制到多个专家。dispatch 必须记住来源 token、目标专家、目标槽位和路由权重。combine 依赖这个 handle 恢复原顺序并完成归并。

自测

问题 1：DeepEP 是否执行专家 MLP 的 grouped GEMM？
否。DeepEP 为专家计算准备按专家组织的输入，并在计算后归并输出。grouped GEMM 由 DeepGEMM、Triton、CANN 算子或其他 MoE runner 执行。
问题 2：为什么 combine 不能只是一次普通 all-to-all？
因为它还要恢复原 token 顺序，并处理 top-k 多路结果、路由权重、可选 bias 和 multiple reduction。通信只是其中一部分。
问题 3：prefill 和 decode 更关注同一种指标吗？
不完全相同。prefill token 多，通常更关注吞吐和链路带宽；decode 每步 token 少，更在意端到端延迟、固定开销和 CUDA/NPU graph 兼容性。EPv2 用统一接口承载这些工作负载，但调度参数仍需按场景选择。
